Ledger Balance Aggregation

A two-process service: one run ingests 50,000 financial transactions into PostgreSQL with concurrency-safe accumulation, then exits; a separate read server serves per-account and total balances in any currency — reading only from the database.

System

Two processes, one channel

The ingest process and the read server never share memory. PostgreSQL is the only thing between them — so both the balances and the exchange rates needed for read-side conversion are persisted. The read server is proven correct after the ingest process has fully exited.

Pipeline

The full flow, end to end

A single deterministic sequence — amber steps compute, blue steps persist or serve.

1
generate · seeded

Synthesize input

A seeded generator writes transactions.csv (50k rows, ~900 ids, 10 dates) and rates.csv — a full grid of every currency × date, so every transaction has a matching rate. USD rate is always 1.0.

2
convert · multiply

Each transaction → USD

usd = (plus − minus) × rate(currency, date) using the transaction's own day's rate. Pure Decimal, no rounding mid-stream.

3
batch · aggregate · sort

Group per id, sort ascending

Rows are batched; duplicate ids within a batch are pre-summed (an ON CONFLICT statement can't touch a row twice), then ids are sorted so every concurrent batch locks rows in the same order.

4
persist · publish

Concurrent upserts → atomic publish

A pool of workers applies batches concurrently into a staging table (balance = balance + Δ under a row lock — no lost updates). One final transaction then publishes staging into the live tables.

5
shutdown

Ingest process exits

The pool closes and the process terminates. Nothing in memory survives — the balances live only in PostgreSQL.

6
serve · fresh

Read server starts

A separate FastAPI process opens its own connection pool and answers reads purely from the database.

7
read · divide

Query & convert

For a non-USD request: value = usd ÷ rate(currency, max_date) using the most recent rate date — same valuation for per-id and total. Money is returned as a JSON string, rounded 2dp HALF_UP.

Bulk load (COPY), same publish

Rates need no transformation or accumulation, so they're loaded in one shot with copy_records_to_table (Postgres COPY) into staging, then published in the same swap. They're persisted so the read server can convert without any of ingestion's in-memory state.

transactions.csv → balances_staging → balances

Accumulating upsert, then atomic publish

Each batch runs one unnest + ON CONFLICT DO UPDATE doing balance = balance + Δ under a row lock — additive, concurrent, no lost updates — into staging. A final single transaction swaps staging into the live tables, so the server keeps serving a consistent snapshot during a reload.

Concurrency

Correct under concurrent writes

Writes are issued concurrently and must never lose an update. Correctness is pushed entirely into one SQL statement — never an app-side read-modify-write.

INSERT INTO balances_staging (id, name, balance_usd)
SELECT * FROM unnest($1::int[], $2::text[], $3::numeric[])
ON CONFLICT (id) DO UPDATE
    SET balance_usd = balances_staging.balance_usd + EXCLUDED.balance_usd;
A

DB-side accumulation

The row-level lock on ON CONFLICT DO UPDATE makes the read-modify-write atomic inside Postgres. Order and interleaving no longer matter — no update is lost.

B

Intra-batch aggregation

A single statement can't affect one row twice, so duplicate ids inside a batch are pre-summed — also shrinking 50k inserts to ~10 batched statements.

C

Consistent lock order

Every batch sorts its ids ascending, so concurrent statements acquire locks in the same order and can't form a deadlock cycle.

Currency

Two conversions, opposite directions

A rate is the multiplier 1 unit of currency → USD. The trap is the direction: ingest multiplies, reads divide.

On ingest · per transaction
usd = (plus − minus) × rate(ccy, date)

Each transaction uses its own day's rate. E.g. 80.00 EUR on a day where EUR=1.0832 → 86.656 USD.

On read · per request
value = usd ÷ rate(ccy, max_date)

Valued at the most recent rate date (2026-06-24, EUR=1.092949). Account 100: 13309.40 USD ÷ 1.092949 = 12177.51 EUR. USD passes through unchanged.
